## Configuration model — source-verified

[job-intake-types.ts](../../lib/jobs/job-intake-types.ts) defines partial `DoorLineInput`, persisted `NativeDoorLine`, glass specifications/results and override metadata. Input is deliberately permissive; TypeScript shape alone is not runtime validation. [normalizeDoorLineInput](../../lib/jobs/door-line-contract.ts) validates and canonicalizes before persistence.

| Concept | Implemented representation and boundary |
| --- | --- |
| Mode/configuration | Interior supports `D`, `DD`, `PKT`, `B.P.`; Exterior supports `D`, `DD` and parsed frame-glass compositions. Common codes are SD, DS, SDS, SDDS and their T/ variants. [Composition parser](../../lib/jobs/glass-unit-composition-contract.ts) accepts repeated S around D/DD and T/; TTT/ is restricted to SDS/SDDS. Bare T is not accepted by this grammar. The common `GLASS_CONFIGS` array is not the full parser grammar. |
| Nominal versus actual size | Width/height select from mode-specific lists; nominal heights are 6'8", 7'0", 8'0". Actual slab dimensions depend on material and sizing path. [Slab modes](../../lib/jobs/slab-sizing-contract.ts) include standard, RO, both custom axes and individual custom axes; legacy `Yes` normalizes to `WoodCustom`. |
| DD sizing | [DD contract](../../lib/jobs/double-door-sizing-contract.ts) supports patio presets, custom active/inactive widths plus shared height, and numeric actual-leaf data. Patio is restricted to Exterior DD with 5' or 6' preset; presets supply actual leaves and height, not a general arbitrary RO. |
| Handing | LH/RH and LHOUT/RHOUT; composition compatibility also recognizes LHOS/RHOS. Side identity is exterior-view left/right. Single-sidelight placement follows [placeSingleSidelightForSwing](../../lib/jobs/glass-unit-composition-contract.ts). Interior outswing is allowed for LOW-PRO; Interior DD also permits a null hand. PKT/B.P. clear hand and jamb fields. |
| Sill/construction | [Construction contract](../../lib/jobs/construction-contract.ts): STD/DARK/NONE select standard, LOW-PRO selects low-profile-quarter-sill, J-4-S selects jamb-four-sides. Stored construction, not legacy free-text sill, selects special geometry. Moving Interior away from LOW-PRO normalizes OUT handing to LH/RH. No-Jamb normalization clears sill and special construction. |
| Glass/panels | Each sidelight specification has side/index, finished width, T-bar, glass code/custom description or panel details. Shared legacy fields remain supported. Transom specification is separate. Codes are CLEAR/SATIN_ETCH/CUSTOM; T-bars are 1.5 or 2.25 inches. Glass units and panel sidelights are different output collections. |
| Other inputs | Quantity, prep, hinges, jamb type/width/RIP, thickness, material, notes and diagram preference belong to the line. Their presence does not mean every field changes geometry. Consult [hinge rules](../../lib/jobs/hinge-contract.ts) and line normalization for allowed choices. |

Interior material normalizes to wood; Exterior accepts wood/fiberglass. Single-door custom slab axes require wood. DD custom sizing has its own validator. Current patio validation checks mode/config/preset, not a fiberglass-only restriction, and the Exterior Material control remains available. Do not infer a fiberglass-only program from the preset name.

## Calculation modules and dimensional conventions

There is no single universal calculator. Two main result contracts share lower-level rules:

| Module | Responsibility / outputs |
| --- | --- |
| [dimension-contract.ts](../../lib/jobs/dimension-contract.ts) | Parse/format dimensions. General dimensions require explicit feet/inches; shop-input parsing accepts numeric inches with a UI-supplied suffix. Stored compatibility accepts either representation. Calculations use numeric inches. Inputs must be positive and on a 1/16-inch grid; formatters round to the nearest 1/16. |
| [non-glass-frame-cut-contract.ts](../../lib/jobs/non-glass-frame-cut-contract.ts) | Interior/Exterior D/DD and Interior B.P.; status Complete/Incomplete/Blocked/Not Applicable, missing fields, blockers, warnings and dimension objects `{inches, display}`. Outputs include actual/final slab, jamb leg, header, sill, outside frame, DD core and cuts. PKT is Not Applicable. B.P. computes finished-opening/door-height information without inventing a frame. |
| [glass-geometry-contract.ts](../../lib/jobs/glass-geometry-contract.ts) | Frame-glass topology, slab resolution, sidelight/panel/transom dimensions, header/jamb/divider values, ordering units, vendor text, issues and exception compatibility. `glassCalc` contains formatted dimension strings plus metadata; it is not a uniformly numeric record. |
| [construction-contract.ts](../../lib/jobs/construction-contract.ts) | Shared construction allowances and 3/4-inch side-jamb thickness. LOW-PRO vertical allowance is 1-5/8 inch. Standard callers can supply path-specific allowances; do not flatten Interior/Exterior/RO rules into one constant. |
| [double-door-astragal-contract.ts](../../lib/jobs/double-door-astragal-contract.ts), [DD sizing](../../lib/jobs/double-door-sizing-contract.ts) | Shared core/leaf and astragal rules, actual-leaf resolution and patio presets. Presentation can suppress an internal astragal instruction without changing its calculation input. |
| [custom-ro-contract.ts](../../lib/jobs/custom-ro-contract.ts) | Shared target/cut helpers. Plain Fit to RO applies to D/DD with `customSlab === 'RO'`, excluding patio. Routine DD reduction is applied to the inactive leaf; reduction over two inches requires review instead of silently cutting. |
| [glass-dimension-reconciliation-contract.ts](../../lib/jobs/glass-dimension-reconciliation-contract.ts) | Converts deliberate dimension commits into consistent source inputs; canonicalizes specifications and reconciles door-core changes against current RO. This is input authority logic, separate from result rendering. |

Header length, DD core, outside frame, RO, slab and ordered glass are distinct dimensions. Non-glass framed `frameWidth` is header plus both side-jamb thicknesses; it is null during DD width review. B.P. has null frame values, and PKT has no applicable frame result. Do not substitute header width for outside frame or fabricate dimensions for Not Applicable results.

Shared formulas do not eliminate all differences: non-glass and glass calculators have distinct assembly paths and nominal-to-actual resolution. For example, non-glass Interior allowances differ from the glass door-core allowance. Reconciliation also performs inverse calculations and rounds source widths. A change must cover forward calculation, inverse reconciliation and serialization together, rather than merely changing a displayed number.

## Input authority and data flow

1. [DoorLineWorkspace](../../components/jobs/DoorLineWorkspace.tsx) owns line editing/defaults; [GlassUnitBuilder](../../components/jobs/GlassUnitBuilder.tsx) commits glass topology/specification/measurement changes. UI drafts can be blank or invalid and are not saved aggregates.
2. Deliberate RO, sidelight-width or transom-width commits go through reconciliation. Direct product-width edits can derive RO; topology/door-core changes reconcile from the **current RO**. Invalid derived widths are retained as invalid source state so the calculator blocks them, rather than keeping stale positive results. Shared specifications populate canonical positional records.
3. Line normalization and [Job service](../../lib/jobs/job-intake-service.ts) validate submitted data; [hosted adapter](../../lib/jobs/hosted-job-intake-repository.ts) normalizes again and maps RPC fields. Add/Update Door in the workspace is not the same boundary as saving the Job to Supabase.
4. Saved inputs and derived fields coexist. Critically, the adapter stores/reconstructs construction, DD sizing and astragal metadata through `glassCalc`; clearing the entire JSON as “just a cache” can lose input authority. SQL has separate direct-specification columns as well.
5. Current presentation calls `withDerivedGlassGeometry`, which replaces calculated units, panels, detail, status, issues, vendor text and override with fresh results even when no `glassCalc` is produced. [Work Order construction](../../lib/jobs/work-order-document-contract.ts) uses this path before output. Incomplete current input must not inherit prior Complete dimensions.

The hosted model has Job revisions and legacy-transfer schema/version/provenance, but no geometry-engine version selector was found in the inspected calculation/persistence path. Reopening or regenerating output can therefore use current formulas for older saved inputs. Job revision pinning prevents a concurrent-save mismatch; it is not formula-version freezing or a historical PDF archive. [Legacy mapping](../../lib/jobs/legacy-transfer-mapping.ts), [validation](../../lib/jobs/legacy-transfer-validation.ts), stored-dimension parsing, and default construction/astragal normalization are compatibility boundaries, not proof every historical record is valid.

## Consumers and separate layout calculations

| Surface | Shared authority and separate work |
| --- | --- |
| Intake/create/edit and saved cards | DoorLineWorkspace uses shared normalization/calculation/reconciliation. Saved-line details recalculate via the glass helper. Mode inheritance, transient text and comparison highlighting are UI state, not domain formulas. |
| Door/glass diagrams | [Diagram contract](../../lib/jobs/glass-diagram-contract.ts) has both calculated physical layout and a builder-only pre-measurement schematic. Physical coordinates are inches, x rightward/y downward with transom above the body; topology uses exterior-view sides. The schematic uses illustrative dimensions and cannot authorize an order. [GlassUnitDiagram](../../components/jobs/GlassUnitDiagram.tsx) renders the layout. |
| Saved Work Order | Document construction recalculates, then passes fresh result values to `calculatePersistedGlassDiagramLayout`. That helper itself does not recalculate despite the upstream freshness guarantee. The diagram separately places parts/dividers and derives DD drawing widths; it is not a second source for cutting dimensions. |
| Preview/PDF | [Preview](../../components/jobs/WorkOrderPreview.tsx), [layout](../../lib/jobs/work-order-layout.ts) and [PDF](../../lib/jobs/work-order-pdf-contract.ts) consume the document model. Font measurement, wrapping, scaling and pagination are output calculations, not manufacturing formulas. |
| Standalone calculator | [StandaloneGlassCalculator](../../components/jobs/StandaloneGlassCalculator.tsx) reuses DoorLineWorkspace and both domain calculators. It has its own compact print presentation/eligibility: Door Calculation without diagram for valid non-glass results, Glass Calculation for glass assemblies. It does not persist a Job. |
| Production scheduling | `calculateJ2AShopHours` in [door-line contract](../../lib/jobs/door-line-contract.ts) estimates workload from active configuration, quantity and preparation/sizing options, not measured glass area. [Job/Calendar synchronization](02-database-and-data-ownership.md) carries saved shop hours/scheduling data. Board capacity calculations are a separate domain; no manufacturing geometry engine was found in that scheduling path. |
| Vendor text | `generateVendorCopy` groups glass units by dimensions/specification. Component counts are per assembly; line quantity is separate. Do not silently multiply quantities or treat panel outputs as glass units. |

## Validation and exceptions

- **Input validation:** required mode/config/nominal choices, positive integer quantity, permitted hand/prep/hinge, jamb requirements, dimension precision and custom sizing are enforced in normalization. Config parsing alone does not authorize Interior frame-glass or every UI state.
- **Geometry validation:** glass requires RO width (including supported automatically derived width) and transom RO height, plus applicable glass/panel specifications. Custom glass needs a description. Standard fiberglass panel widths are 11-3/4 or 13-3/4 inches; custom panel records have separate requirements. Missing details can return `Glass Detail Needed`; malformed/impossible geometry can block. Some non-geometric missing details retain calculable dimensions, unlike missing required measurements.
- **Separate status contracts:** non-glass Incomplete/Not Applicable and glass Detail Needed/Unsupported are not interchangeable. [Status presentation](../../lib/jobs/status-presentation.ts) translates internal statuses; [preflight](../../lib/jobs/work-order-preflight-contract.ts) determines blockers and acknowledgement. A saved Draft may need more details; saving, production readiness and print acknowledgement are distinct decisions.
- **Geometry Exception:** `applyManualGeometryOverride` requires Jobs use, a warning with measured geometry and no blocker, stable line ID, reason and accepted values. Approval records calculated/accepted snapshots and actor/time. Recalculation validates snapshot compatibility; it does not turn arbitrary incomplete/blocked geometry into Complete. Geometry field changes can invalidate approval. See [exception tests](../../lib/jobs/geometry-exception.test.ts).
- **Browser/server/database:** the browser gives immediate feedback; service/adapter normalization repeats application validation. [SQL direct-dimension extension](../../supabase/migrations/20260805000000_add_direct_dimension_glass_sources.sql) validates payload types/enums/specification constraints; [update allowlist correction](../../supabase/migrations/20260805010000_fix_direct_dimension_update_rpc_allowlist.sql) and later patches affect effective persistence. SQL does not duplicate the TypeScript manufacturing engine. Schema acceptance alone does not establish valid geometry; effective migration history is covered in Task 2.

## Regression risks, tests and unknowns

Highest-risk changes are shared construction/DD allowances, nominal-to-actual sizing, 1/16 rounding, exterior-view handing, topology reconciliation, JSON input metadata, override snapshot equality, and output freshness. PDF and diagram changes can misrepresent correct calculations without changing a formula. Keep text labels and production dimensions separate when reviewing presentation fixes.

**Potential concerns needing focused investigation:** physical DD drawing code resolves equal visual leaf widths from its assembly/slab inputs; verify unequal custom-leaf diagrams against numeric results before treating the illustration as fabrication authority. Parser support for repeated sidelights exceeds the common configuration list; exhaustive supported combinations and manufacturing acceptance were not established. Patio Material permissiveness is source behavior, not confirmation of vendor/product policy.

**Unverified:** full cross-product coverage of mode × material × construction × sizing × topology × handing; actual browser-to-hosted round trips for old records; live SQL constraints and migration drift; independent manufacturing tolerances beyond coded rules; current test pass status. Existing tests do not constitute proof of these cases. A dedicated coverage audit is needed before declaring specific combinations untested. No geometry-version migration strategy was found; future formula changes need an explicit existing-job/output compatibility decision.
